# The config export is the only path to what the API cannot see in v1: opt-in, redacted before persistence, raw never stored, SSH deferred

The [allowlist lab run](https://github.com/andrewferk/opnsense-pilot/issues/13) fixed the coverage gaps of the native API on Community 26.7.4: per-interface IP configuration, PPP, scrub rules, schedules, ISC DHCP server configuration, general and advanced system settings, NTP, and auth servers have no API at all; gateway groups, legacy outbound NAT, and the legacy-rule migration counts exist but a least-privilege account cannot reach them; stored source NAT rules are hidden outside hybrid or manual mode. The [first detector](https://github.com/andrewferk/opnsense-pilot/issues/16) also wants the config export as its primary evidence. One call, `GET /api/core/backup/download/this`, closes every gap, but it returns the whole `config.xml` with every secret on the box, and the only privilege that grants it, "Diagnostics: Configuration History" (`api/core/backup/*`), also grants the POST-only backup revert and delete actions; upstream has no finer privilege and no secrets-free export, only whole-file password encryption on the legacy page. The alternative the handoff allowed, a read-only SSH adapter running allowlisted `configctl` actions, turns out to be no narrower: only all-pages admins in `wheel` can log in over SSH at all, `config.xml` is group-readable by `wheel`, the configd socket is world-writable and configd runs as root, and no `configctl` action reads the configuration of any gap category anyway (only runtime state for interfaces and NTP). Read-only would be a property of the commands chosen, never of the channel.

We decided that **the config export is the only gap path in v1**, consumed by one parser whether it arrives live over the API or as a locally supplied file. **Live export is a per-firewall opt-in, off by default**; when off, export-derived categories abstain with the reason "export not enabled" and the CLI offers the local import. **The raw export is never persisted**: it is parsed in memory, redacted, and only the redacted document plus the normalized inventory are stored as private observations. **Inventory prefers the reviewed API path** and the export back-fills only what the API cannot see for that release range; detectors choose their own evidence independently. **A read-only SSH adapter is out of scope for v1.** We rejected SSH because it needs a root-equivalent account, a second transport, host-key handling, and an optional dependency to reach data the export already holds. We rejected covering every section the export reaches because v1 promises only the target inventory (interfaces, firewall and NAT rules, gateways, routes, services, DNS and DHCP, WireGuard); other sections report "not collected, outside v1 inventory" rather than becoming half-supported categories. We rejected default-on live export because it is a secret-bearing read behind a privilege that also permits destructive actions, and the administrator should grant that knowingly. We rejected encrypted raw retention because it belongs to the write path's pre-change backups, not to a read-only slice.

## Consequences

- **Consent and docs.** Enabling live export requires the Pilot account to hold "Diagnostics: Configuration History". The documentation and the enable step state that this privilege also permits backup revert and delete over the API, that the typed operation registry (not the privilege) is what keeps Pilot read-only, and that the export contains every secret on the firewall and is redacted before anything is stored. The registry entry for the export carries its own side-effect class, secret-bearing read, so it can be gated separately from ordinary reads.
- **Redaction.** A reviewed list of secret element paths is the promise; a name heuristic (password, secret, key, psk, privkey, passphrase, token, apikey and similar) is the safety net; a final scanner pass over the redacted document (PEM blocks, long base64 runs, the secret shapes seen in the lab fixtures) rejects the export outright if anything survives. Redaction replaces each value with a marker so "present but redacted" remains a fact for detectors. Values caught by the heuristic but missing from the reviewed list are counted and surfaced on the snapshot as unreviewed redactions, so the list grows from real data. A redaction failure yields no snapshot, never a partial one.
- **Coverage is explicit.** Every inventory category carries a coverage value (collected, partial, not collected) and, when not collected, a reason from a fixed set: no API, privilege denied, export not enabled, plugin absent, outside v1 inventory, unsupported release. Coverage travels with the snapshot through CLI, REST, and MCP; an uncollected category is never rendered as an empty list.
- **Mixed evidence is labelled, not forbidden.** One snapshot per firewall records, per category, its evidence source (API, live export, imported export) and time. An import records where the file came from, its hash, and the import time, so a stale import can be flagged. Disagreement between sources is handled by detectors, which abstain and cite both items.
- **Release version on import.** A config export carries no product version (only per-model schema versions and the last revision), so an import-only firewall cannot satisfy a version-gated detector by itself. The user declares the release at import; the snapshot records it as user-asserted evidence at the "degraded" confidence tier of [the version-mapping decision](https://github.com/andrewferk/opnsense-pilot/issues/4), while the firmware API's build hash is "exact". When both exist and disagree, version-gated detectors abstain citing both. Inferring the release from model schema versions is a research lead, not a v1 mechanism.
- **Per-release paths.** Gateway groups are export-only on 26.7.4 and move to the API path once the upstream ACL fix ([opnsense/core#10909](https://github.com/opnsense/core/pull/10909)) ships in a later 26.7.x; the registry expresses this as one path per entry per release range.
- **SSH later, if ever.** A future SSH or `configctl` adapter would be a fresh effort aimed at runtime diagnostics the export cannot answer, and would have to face the same root-equivalence facts recorded here.

Facts verified on the probe VM (26.7.4_1) and in `opnsense/core` at master `cc6419c7f` on 2026-09-23; details on [map ticket #25](https://github.com/andrewferk/opnsense-pilot/issues/25).
