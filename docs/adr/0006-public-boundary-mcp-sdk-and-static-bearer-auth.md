# The public boundary: official MCP SDK 2.x serving both protocol eras, static client tokens behind a verifier seam

The handoff fixes MCP over Streamable HTTP as the public agent interface and asks us to use a maintained SDK, pin and test the negotiated protocol version, and pick an authorization deployment. We commit to the **official `mcp` Python SDK on the 2.x line** (`mcp>=2.2,<3`, exact version locked), **serving both protocol eras** (`2026-07-28` and the handshake era up to `2025-11-25`) from one endpoint, and **static named client tokens** checked by our own ASGI middleware, over loopback or TLS. Each request resolves to a principal that the service layer scopes authorization to, so the spec's OAuth 2.1 resource-server mode is a configuration change later, not a rewrite.

We rejected **FastMCP 4.x**: it is a layer over the same SDK that adds OAuth proxies, composition, and dependencies v1 does not need. We rejected **`mcp` 1.x**: maintenance mode, stopping at protocol `2025-11-25`. We rejected **OAuth for v1**: it is the specification's authorization model, but it requires running and securing an authorization server for a single-user LAN install, and both target clients accept a static bearer today. We rejected **refusing legacy-era requests**: it would lock out OpenAI Codex CLI's default mode. The two-client transport test ([map ticket #14](https://github.com/andrewferk/opnsense-pilot/issues/14)) ran this exact stack against Claude Code 2.1.278 and Codex CLI 0.155.1 in both eras with a static bearer and found nothing that changes it.

## Consequences

- **Version policy is a test, not a setting.** The SDK cannot disable an era. CI asserts over a real socket that `server/discover` advertises exactly the expected version set, that the SDK client negotiates `2026-07-28` in auto mode and `2025-11-25` in legacy mode, and that version errors, Host (421), Origin (403), and body-cap (413) responses hold. An SDK bump that changes the set fails CI until someone updates the snapshot, reads the release notes, and updates the compatibility statement. The compatibility statement names the tested clients at their tested versions.
- **Client tokens.** More than one token, each with a name, generated by a CLI command and stored as hashes in a config-referenced secrets file or environment variables, never in the database and never in the repository. Rotation is create-new then revoke-old. The middleware compares in constant time, answers `401` with `WWW-Authenticate: Bearer` and no `resource_metadata` (there is no authorization server to discover), never accepts a token in the query string, and never logs token material. The SDK's `AuthSettings` is not used with static tokens because it would publish metadata pointing at an authorization server that does not exist.
- **Principal scoping from day one.** The middleware sits behind a verifier-shaped seam that yields a principal (in v1, the client token's name). The service layer denies by default and scopes firewalls, snapshots, and resources to the principal, even though v1 grants every token access to every registered firewall. Multi-user later means an OAuth 2.1 resource server in our process (the SDK's `TokenVerifier` and `AuthSettings`) with an external authorization server such as Keycloak or Authelia, HTTPS everywhere, and per-principal grants; nothing at the tool or service layer changes.
- **No token passthrough, structurally.** The client token authenticates the agent to Pilot. The OPNsense API credential is a separate server-side secret and is never forwarded.
- **Network exposure.** The service binds `127.0.0.1` by default and always passes explicit `TransportSecuritySettings` (a non-localhost host silently disables the SDK's Host and Origin checks). A non-loopback bind requires TLS, either certificates on uvicorn or a declared trusted reverse proxy with forwarded-header trust limited to that proxy; otherwise the service refuses to start. There is no plain-HTTP escape hatch in v1. Client trust of a private CA is untested and is a v1 plan task.
- **One process.** MCP is mounted inside the FastAPI application under `/mcp`, REST under `/v1`, one uvicorn, `session_manager.run()` entered from the FastAPI lifespan (a mounted app's lifespan never runs on its own). One middleware guards both REST and MCP. Health stays on the FastAPI side, unauthenticated. `stateless_http=True`: v1 tools never call back into the client, so no session state is held.
- **Discoverable surface.** Claude Code never lists resource templates, so anything an agent must discover is a tool or a listed static resource; templates are reachable only by a URI the agent already holds. Advertised capabilities are trimmed to what the server offers when the SDK exposes a knob; otherwise the idle stream Claude Code opens is accepted.
- Evidence at decision time (2026-09-23): SDK research in [map ticket #7](https://github.com/andrewferk/opnsense-pilot/issues/7) (`mcp` 2.2.0, specification `2026-07-28`), transport matrix in [map ticket #14](https://github.com/andrewferk/opnsense-pilot/issues/14), decision in [map ticket #22](https://github.com/andrewferk/opnsense-pilot/issues/22).
