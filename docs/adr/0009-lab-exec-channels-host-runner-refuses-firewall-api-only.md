# Lab exec channels: the default environment refuses, the firewall is a named target reachable only by API, and the scenario image carries no SSH

[The Inspect QEMU research](https://github.com/andrewferk/opnsense-pilot/issues/24) settled that the lab is a custom Inspect `SandboxEnvironment` provider over an Inspect-free lab controller, with the firewall a named environment and never the first entry of `sample_init`'s dict. It left open what the first entry is, which channel the provider's `exec`, `write_file`, and `read_file` use on the firewall, and how orphaned processes are swept. In v1 the agent under test is the OPNsense Pilot service driven over MCP from the host process and scorers are Python, so nothing inside a sample needs a shell anywhere; the handoff requires scorers to hold independent credentials the agent cannot edit; and the only shells the firewall offers today are the serial console (csh, a 1,000-character line limit, login state unknown after a warm restore) and SSH, which on OPNsense admits only all-pages administrators in `wheel` ([ADR 0008](0008-config-export-is-the-only-gap-path-in-v1.md)).

We decided that **the default environment is a host-side runner whose `exec`, `write_file`, and `read_file` refuse** in v1; it exists so the firewall is never Inspect's default and so any tool that expects a shell (`bash()`, `bash_session`, `text_editor`, restic checkpoints) fails loudly instead of running on the developer's Mac. **The firewall is a target environment reachable only through its API**: the provider's `exec`, `write_file`, and `read_file` refuse on it too, and scorers read the firewall with a distinct read-only scorer API user whose key lives with the lab controller. **The serial console is controller-only** (boot readiness, recovery, image preparation) and is never surfaced through the provider. **The scenario image runs no SSH service and holds no SSH key.** Together these give the lab the property that a sample holds no mutation path: nothing inside it (agent, tools, scorers) can change firewall state, because scenario injection happens before the scenario baseline snapshot is taken. We rejected a local-style host environment because Inspect's own docs confine the local sandbox to use inside another sandbox and scorers can call the Pilot library and the lab controller directly in Python. We rejected an arm64 client VM as the default because no v1 scenario gives the agent a shell; a client VM remains a lab acceptance criterion (it proves the Unix-socket segment across TCG and HVF QEMUs) and can become the default in a later effort. We rejected the serial console and a baked SSH key as the firewall `exec` channel because both are root-equivalent write channels whose only v1 consumer would have been scorer evidence the API already supplies. We rejected a standalone TTL sweeper daemon: the controller keeps a run registry (process ids, sockets, overlays, start time, run id) that `inspect sandbox cleanup qemu` reads and that `task_init` sweeps for dead or over-TTL entries before acquiring a firewall slot; the same registry serves pytest runs that never go through Inspect.

## Consequences

- **Scorer ground truth** is the scenario definition plus an independent API read with the scorer user; a v1 scorer that needs evidence the API cannot give (pf tables, captures, files under `/conf`) is a scope change that reopens the firewall channel, not a quiet workaround.
- **Scorer user in the golden image.** The image carries a `pilot-scorer` API user with the same read-only privilege set as `pilot-readonly` and its own key, so audit logs distinguish agent reads from scorer reads. Keys stay in the lab's credentials file, outside the repo.
- **Testable property.** The lab issue's acceptance criteria include enumerating every channel the provider exposes and asserting that none reaches the firewall with write ability.
- **Later shells are additive.** A scenario that needs an agent shell adds a client VM as the default environment; a scenario that needs runtime diagnostics off the firewall adds SSH to that scenario's image under a fresh decision. Neither changes the firewall's refusing `exec`.
