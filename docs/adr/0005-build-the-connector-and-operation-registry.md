# We build our own OPNsense connector, and a reviewed operation registry is the read-only control

The handoff fixes httpx as the OPNsense API client and asks for a "cited comparison and thin prototype" before choosing whether to reuse an existing client or MCP project. The comparison ([map ticket #6](https://github.com/andrewferk/opnsense-pilot/issues/6), 15 Python clients and 13 MCP servers read at pinned commits) found nothing to adopt or wrap: every general-purpose client puts reboot, upgrade, and rule writes on the same object as reads, none fails closed, none returns reviewed typed models, the best-maintained one requires Python 3.14 and aiohttp, and the closest stack matches are GPL-3.0, AGPL-3.0, or unlicensed, which [ADR 0002](0002-bsd-2-clause-license-and-upstream-material.md) rules out. We therefore **build a thin async httpx plus Pydantic v2 connector of our own**, borrow designs and permissively licensed seed data with notices, and vendor no code. The lab run against the probe VM ([map ticket #13](https://github.com/andrewferk/opnsense-pilot/issues/13)) stood in for the prototype: the transport is the cheap part, and it works unchanged on HTTP/1.1.

A future reader who finds `pyopnsense` or `oxl-opnsense-client` on PyPI will wonder why we wrote another. The answer is that the HTTP layer was never the value. What nobody provides in a form we can trust is the per-release **operation registry**: one entry per reviewed native call, with the verb pinned, a fixed payload shape, a verified release range, the privileges it needs, its side-effect class, the fields to redact, a source citation at the pinned commit, and the lab evidence that passed. The registry, not the HTTP verb and not OPNsense's ACLs, is the fail-closed control that makes v1 read-only: the connector can only issue registered operations, a missing entry is `UNSUPPORTED_CAPABILITY`, and a non-read entry is `POLICY_DENIED`. OPNsense ACLs cannot make a user read-only (ticket #13 showed a "deny config write" account could still reload the firewall), and a wrong-verb call returns a misleading 200, so neither could serve as the control.

## Considered options

- **Wrap a permissive client** (for example `lucamarien/opnsense-mcp-server`, MIT) behind our allowlist. Rejected: the read-only guarantee would rest on never calling half of a dependency, and its deny-list safety model is the opposite of ours.
- **Adopt a client outright.** Rejected for the reasons above plus the license and Python-version conflicts.
- **Seed the registry from the upstream API-doc generator.** Rejected as the proposal stage by [map ticket #8](https://github.com/andrewferk/opnsense-pilot/issues/8): it defaults 28% of core actions to GET, including verified mutators, misses inherited and `__call` actions, and carries no ACL or side-effect evidence. It stays as a CI cross-check that our extracted action set is a superset of its output at the same pinned ref.

## Consequences

- **Candidates are proposed mechanically, entries are promoted by review.** A Tree-sitter extractor over core and plugins at the pinned ref emits candidate operations (module, controller, command, base class, and any `isPost` or write evidence it finds) into a generated file that is diffed, never imported at runtime. A reviewer fills the verb, privileges, side-effect class, and lab evidence before a candidate becomes an entry. Drift at a new ref is a diff of candidates against entries. Third-party maps, such as the Apache-2.0 hass-opnsense endpoint-to-privilege table, may be imported as candidates with a notice in `THIRD-PARTY-NOTICES.md`, never as entries.
- **The registry is code**: typed Python objects in a reviewed module, type-checked under strict pyright and importable by tests and the Inspect harness without a loader. Not YAML, not database rows.
- **v1 registers only `read` entries and individually reviewed `read-with-job` entries.** Side-effect classes are `read`, `read-with-job` (a read that starts a background job upstream, such as some firmware calls), and `mutation`. No `mutation` entry exists in the v1 codebase.
- **One path per entry per release range, no fallback probing.** v1's range is 26.7.x. Outside a verified range the connector returns `UNSUPPORTED_VERSION` and detectors abstain. A second target release means new entries with their own ranges, not aliases or camelCase-to-snake_case guessing.
- **Connector requirements from the lab are its contract tests**: async httpx on HTTP/1.1 only (HTTP/2-only fails against 26.7.4 and `http2=True` silently stays on 1.1); never follow redirects (a credential-less request gets a 302); no `Content-Type` header on a body-less GET (400); verb pinned per operation; verified TLS with no disable switch; bounded timeouts with a read-only retry policy of bounded backoff and deadlines.
- **Transport outcomes map to the handoff's error codes at the connector boundary**: 401, or a 302 with no credentials, is `UNAUTHORIZED`; 403 from OPNsense's ACL is `POLICY_DENIED`; 404 is `UNSUPPORTED_CAPABILITY`; a timeout is `UPSTREAM_TIMEOUT`; a 500 "denied for write access" is a refused mutation that the registry should never have let through, reported loudly as a registry defect. A permission error is never evidence that a feature is absent.
- Vocabulary (connector, operation, candidate operation, operation registry) is defined in `CONTEXT.md`. Details and the reuse shortlist are in [map ticket #20](https://github.com/andrewferk/opnsense-pilot/issues/20).
