# Existing OPNsense clients and MCP projects: reuse survey

- **Ticket:** [#6](https://github.com/andrewferk/opnsense-pilot/issues/6) (map: [#2](https://github.com/andrewferk/opnsense-pilot/issues/2))
- **Survey date:** 2026-09-19
- **Method:** candidates found with `gh search repos`, PyPI JSON metadata, and web search; every repository below was downloaded at the commit shown and read locally (README, source, tests, LICENSE, packaging). Metadata (stars, last commit, releases, contributors) came from the GitHub REST API on the survey date. Nothing here is described from memory. No candidate was installed, executed, or pointed at a firewall: **all findings are static reads of source and docs, not behavioural tests.**
- **Criteria** (handoff section 12 and the ticket): maintenance, license, async support, TLS verification default, ACL/least-privilege posture, OPNsense version coverage and handling, tests, mutations or arbitrary passthrough, typed models, and the cost of extending to a typed, allowlisted, read-only operation registry on httpx + Pydantic v2 (Python 3.13 first, per handoff section 3).

## Recommendation

**Overall: build our own thin httpx + Pydantic v2 adapter; adopt nothing, wrap nothing, borrow ideas (and a small amount of permissively licensed reference data) from five projects.**

No surveyed project can be adopted or wrapped without breaking a handoff constraint:

1. **Every general-purpose Python client exposes mutations** (reboot, firmware upgrade, rule/alias writes, service control) on the same object as the reads. Wrapping one means our read-only guarantee rests on never calling half of a dependency's public surface, and its transport has no allowlist to fail closed on. Our registry needs the opposite shape: the transport refuses anything not registered.
2. **None returns reviewed, validated typed models for reads.** `aiopnsense` returns `dict`/`list`; `oxl-opnsense-client` returns Ansible-style result dicts; the clients that do have Pydantic models (`opn-api`, `opnsense-py`) are AGPL-3.0 or unlicensed; `opnsense-openapi` generates models from schemas inferred out of PHP source, which is not a reviewed contract.
3. **The best-maintained client is incompatible with the baseline.** `aiopnsense` requires Python >= 3.14 and aiohttp; the handoff fixes Python 3.13 first and httpx. That is a concrete incompatibility, not a preference.
4. **License exposure.** The project license is not yet chosen (handoff sections 11 and 13). GPL-3.0 (`oxl-opnsense-client`, `pyopnsense`), AGPL-3.0 (`opn-api`, `gabrielion/OPNSenseMCP`, `floriangrousset`), and unlicensed (`opnsense-py`, `aesaganda`, `digitalhen`) code cannot be copied without deciding that question for us. Ideas are free; code is not.
5. **The HTTP layer is the cheap part.** OPNsense auth is HTTP Basic with key/secret over TLS; the surveyed transports are 100 to 800 lines. The expensive part (per-release operation mappings with privilege needs, source evidence, and lab proof) is exactly what no project provides in a form we can trust without redoing the verification.

## Per-project notes

### Snuffy2/aiopnsense and travisghansen/hass-opnsense

- The README states it "was extracted from the hass-opnsense integration" and is used by both hass-opnsense and Home Assistant's OPNsense integration ([README](https://github.com/Snuffy2/aiopnsense/blob/310fbe9ec0/README.md)). That user base is the strongest maintenance signal in the survey, but the GitHub repo is six months old (created 2026-03-20) with one human committer.
- `pyproject.toml` sets `requires-python = ">=3.14"` and depends on `aiohttp`, `awesomeversion`, `python-dateutil`. Both conflict with the handoff baseline (Python 3.13 first, httpx).
- Version handling is explicit and worth copying as a pattern: [`const.py`](https://github.com/Snuffy2/aiopnsense/blob/310fbe9ec0/aiopnsense/const.py) names each behavioural boundary (`OPNSENSE_MIN_FIRMWARE = "25.1"`, `LEGACY_CAMELCASE_ENDPOINT_FIRMWARE = "25.7"`, `LEGACY_UNBOUND_BLOCKLIST_FIRMWARE = "25.7.8"`, `OPNSENSE_LTD_FIRMWARE = "26.1.1"`, `UNIFIED_NAT_TEMPLATE_FIRMWARE = "26.1.4"`, `OPNSENSE_26_1_11_COMPAT_FIRMWARE = "26.1.11"`). These are leads for our compatibility research, not facts to copy: each must be confirmed against upstream source at a pinned tag per the map's evidence discipline.
- [`client_endpoint.py`](https://github.com/Snuffy2/aiopnsense/blob/310fbe9ec0/aiopnsense/client_endpoint.py) caches endpoint availability and distinguishes permission-denied from missing. This matches the handoff rule that "a permission error is not evidence that a feature is absent".
- [`docs/granular_permissions.md`](https://github.com/travisghansen/hass-opnsense/blob/1fc19708c8/docs/granular_permissions.md) maps each endpoint to the OPNsense privilege that grants it, with both path spellings and privilege names that changed between 25.x and 26.1. It also records that the ISC DHCP `service/status` endpoints have no privilege narrower than "All pages". The hass-opnsense README still recommends an admin user as the simple path, so least privilege is documented but opt-in.
- Returns are plain `dict`/`list`. We would validate every response ourselves anyway, so the client would save us only URL strings.

### O-X-L/opnsense-api-client

- A mechanical port of the Ansible collection: `run_module(name, params)` with Ansible-style specs and `changed`/`diff` results ([README](https://github.com/O-X-L/opnsense-api-client/blob/7dc2d1ab23/README.md)). Its centre of gravity is idempotent writes; reads go through a `list` module.
- `requirements.txt` is `httpx` plus `ansible-core==2.19.*` "only for module-spec validation". That is a heavy, exactly-pinned transitive dependency.
- A [`raw` module](https://github.com/O-X-L/opnsense-api-client/tree/7dc2d1ab23/src/oxl_opnsense_client/plugins/modules) exists (arbitrary endpoint calls).
- TLS defaults are good: `ssl_verify=True` with a CA bundle path, and the README labels disabling it "ONLY USE FOR TESTING PURPOSES".
- GPL-3.0 would force Pilot's license choice if imported as a library.

### endavis/opnsense-openapi

- Downloads OPNsense source for a version, parses PHP controllers, emits OpenAPI 3.0, and generates a client; 56 specs are bundled from 24.1 through 26.1.6 ([specs dir](https://github.com/endavis/opnsense-openapi/tree/87ac086817/src/opnsense_openapi/specs)).
- HTTP methods are **guessed from the action name** ([`controller_parser.py` `_guess_http_method`](https://github.com/endavis/opnsense-openapi/blob/87ac086817/src/opnsense_openapi/parser/controller_parser.py), "Default to POST for safety"). For a project whose safety property is "reads only", a heuristic method classifier is not acceptable evidence. The upstream docs collector ([`lib/__init__.py`](https://github.com/opnsense/docs/blob/935c07c206/lib/__init__.py)) parses a PHP AST and detects `isPost`/`isGet` calls, which is a better basis; note that many OPNsense read endpoints (searches) legitimately use POST, so HTTP method alone never proves read-only either.
- The client auto-generates code on first use ("takes ~2 minutes"), which is the opposite of a reviewed, pinned registry.
- Useful as a diffing aid: bundled per-point-release specs could quickly show when a path appears or disappears, as a lead to confirm in source.

### by-openclaw/lib-opnsense

- Async httpx, typed exceptions, frozen dataclass models, retry. Architecturally tidy, but every manager is CRUD + `ensure()`, and the README marks it "Internal use".
- `verify_ssl` defaults to `False` in both the client and the credential provider ([`client.py` L82](https://github.com/by-openclaw/lib-opnsense/blob/b7e0dd4dc0/src/opnsense/client.py), [`credentials.py`](https://github.com/by-openclaw/lib-opnsense/blob/b7e0dd4dc0/src/opnsense/credentials.py)).
- [`docs/api/discovery-methodology.md`](https://github.com/by-openclaw/lib-opnsense/blob/b7e0dd4dc0/docs/api/discovery-methodology.md) and the delta docs (for example [`26.1.9-to-26.7-delta.md`](https://github.com/by-openclaw/lib-opnsense/blob/b7e0dd4dc0/docs/api/26.1.9-to-26.7-delta.md), which reports 205 endpoint schema files changed) show a repeatable way to capture drift from a lab VM. Their numbers are their claims; we have not reproduced them.

### gabrielion/OPNSenseMCP

- Deliberately tiny read surface (`server_status`, `opn_describe`, `opn_get`, `opn_list` over `system.status`, `core.services`, `firewall.alias` host entries) with strict JSON Schemas, `additionalProperties: false`, and bounded sizes in [`operation-contract.v1.json`](https://github.com/gabrielion/OPNSenseMCP/blob/769bf47248/src/operations/operation-contract.v1.json).
- Security posture closest to the handoff: TLS "always remains enabled"; config file must be `0600`, single hard link, non-symlink; diagnostics are deliberately opaque; write tools are not even listed when `READ_ONLY=true`; legacy SSE never gets writes ([README](https://github.com/gabrielion/OPNSenseMCP/blob/769bf47248/README.md)).
- The [setup guide](https://github.com/gabrielion/OPNSenseMCP/blob/769bf47248/docs/setup-your-opnsense.md) grants exactly three privileges and notes that `/api/core/firmware/status` correctly returns 403 for that account: a concrete example of our "limited account collects real data" done-criterion and of treating 403 as expected.
- Risks as a dependency (not that we could use it): AGPL-3.0, TypeScript, single author, preview status, 0 stars, a month since last commit on the default branch.

### lucamarien/opnsense-mcp-server

- [`api_client.py`](https://github.com/lucamarien/opnsense-mcp-server/blob/d4d0bd2489/src/opnsense_mcp/api_client.py) is the nearest thing to the adapter we need: async httpx, `ENDPOINT_REGISTRY` of logical names to (camelCase, snake_case) paths, version detection, and a missing-endpoint classifier. It is untyped (`dict[str, Any]`) and its safety net is a five-entry deny-list, so anything not on the list is callable once writes are enabled.
- Exposes `opn_download_config` / `opn_get_config_section` (full `config.xml` reads). For Pilot this is a redaction and privilege question to settle under the export/SSH gap item on the map, not something to copy.
- The README states that OPNsense 26.7 removed the savepoint/rollback API and that the server probes for it rather than hardcoding a cut-off. This is relevant to M3+ write-path planning only, and is **unverified here** (third-party claim; confirm in upstream source before relying on it).

### Field notes worth carrying forward (all unverified third-party claims)

- [vpciii/opn-mcp README](https://github.com/vpciii/opn-mcp/blob/dc1f031a71/README.md): OPNsense 26.7's web server "emits malformed HTTP/1.1 chunked framing on API responses past roughly 100 KB", surfacing in httpx as `RemoteProtocolError: malformed chunk footer`; their workaround is negotiating HTTP/2. Since Pilot uses httpx, reproduce this on the probe VM with a large log fetch before fixing transport settings.
- [tazendor README](https://github.com/tazendor/opnsense-mcp-server/blob/a6f3062b90/README.md): 26.x "made breaking REST API changes": Kea replacing ISC DHCPv4 paths, port-forward NAT moving to `firewall/d_nat/*`, and a changed system status endpoint.
- Several projects (aiopnsense, lucamarien, opn-api, kisst) independently agree that API paths moved from camelCase to snake_case at 25.7. Independent agreement is a strong lead; the compatibility-target ticket should still confirm it in `opnsense/core` at pinned tags.

### Patterns to avoid, seen repeatedly

- README quick-start snippets that set `VERIFY_SSL=false` even when the code default is secure (lucamarien, vespo92, Pixelworlds, endavis, opn-api). Users copy examples. Pilot's docs should show the CA-file path as the primary example and offer no "disable verification" switch on the public surface.
- Deny-lists for dangerous endpoints (lucamarien, floriangrousset, aesaganda). They fail open on anything new upstream. An allowlist fails closed.
- "Read-only mode" implemented as a runtime flag over a client that can write. Pilot's v1 transport should be incapable of issuing unregistered requests, and the OPNsense account should be unable to mutate even if it did.
- Recommending an admin-role API user as the default (hass-opnsense README; lucamarien's "default API access is sufficient").

## Open uncertainties

1. **Nothing was executed.** TLS defaults, write gating, and version detection are as read in source at the pinned commits, not observed behaviour.
2. **Privilege map accuracy.** The hass-opnsense permission table is the best seed available but is maintained for that integration's endpoint set and is unverified against our target release; each entry we use needs lab confirmation with a limited account.
3. **Version-boundary claims** (25.7 snake_case, 26.1 Kea/NAT moves, 26.7 savepoint removal and chunked-framing issue) are third-party statements. They belong in the risk register as leads for the compatibility-target and lab tickets.
4. **Young, fast-moving repos.** Most MCP servers and two of the better clients were created in 2026 and have one author; several show very high recent commit counts. Rankings here could change within months; re-check before any later reuse decision (for example at M3).
5. **Search coverage.** GitHub, PyPI, and one web search were used. GitLab/Codeberg/Forgejo-hosted projects (one candidate, `coreyhines/opnsense-mcp`, has a `.forgejo` directory, and `pacyworld/opnsense-mcp` is a mirror) and npm-only packages were not searched systematically. Non-Python clients (Go, TypeScript, Terraform providers) were out of scope except where an MCP server embedded one.
6. **License borrowing.** "Borrow ideas" from Apache-2.0/MIT projects may include small data (for example privilege names) with attribution; whether to copy any text or tables verbatim should wait for Pilot's own license decision and keep upstream notices, per handoff section 11.
