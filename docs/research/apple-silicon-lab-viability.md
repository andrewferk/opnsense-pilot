# Is an emulated-amd64 OPNsense lab viable on Apple Silicon?

Research for [issue #5](https://github.com/andrewferk/opnsense-pilot/issues/5). Researched 2026-09-19. Reading research only: nothing was installed or booted. Every performance statement below is either a cited third-party report (labelled **anecdotal**) or an explicit unknown for the probe VM.

Host checked (read-only `sysctl` / `sw_vers` / `which`): Apple M4 Pro, 12 cores (8 performance + 4 efficiency), 24 GB RAM, macOS 26.7, `kern.hv_support=1`, about 370 GiB free disk. Docker Desktop is installed (daemon not running at check time). No `qemu-system-*`, `utmctl`, `limactl`, or `packer` on `PATH`.

## Verdict

**Viable on paper, not yet proven; go ahead with the probe VM.** Nothing in the primary sources blocks it, and every building block the lab needs is a documented, supported QEMU feature on an arm64 macOS host. What is missing is trustworthy first-hand evidence of how *fast* OPNsense is under TCG on this class of machine: the only OPNsense-specific report found is one 2021 forum post ("runs, feels very slow", M1 Air, via UTM). Speed is therefore the single question the probe must answer, and it is the only plausible way this turns into "not viable".

Supporting facts, each cited below:

1. QEMU's TCG accelerator officially supports macOS hosts on Arm and emulates x86; HVF only accelerates same-architecture guests, so an amd64 guest on this Mac is always TCG.
2. Multi-threaded TCG is on by default for x86 guests in current QEMU (checked in source at v10.1.0 and v11.1.0), so a 2-vCPU firewall can use two host cores.
3. FreeBSD amd64 under QEMU TCG is a documented, mainstream configuration: the FreeBSD Handbook's whole QEMU chapter uses TCG.
4. OPNsense ships an official preinstalled `nano` amd64 image with a serial primary console, so the probe needs no installer run and no GUI.
5. There is no official aarch64 OPNsense. The community aarch64 build is explicitly unsupported by the OPNsense team, so it cannot be the compatibility target.

## Recommended approach for the thin probe VM

Needs the owner's go-ahead because it installs software (`brew install qemu`). No root, no kernel extensions, no daemons.

1. **Runner: plain QEMU from Homebrew**, not UTM, Lima, or Docker. Homebrew's `qemu` formula is at 11.1.1 with arm64 macOS bottles, built with `--enable-slirp` and `--enable-vde`.
2. **Image: official `OPNsense-<release>-nano-amd64.img.bz2`** from the official mirror, signature-verified, decompressed, converted to qcow2 (`qemu-img convert`), and grown (`qemu-img resize`). The nano image is preinstalled with serial as primary console, so first boot lands at a login prompt on the serial port. Release choice belongs to the compatibility-target ticket; 26.7 was the current series on the mirror at research time.
3. **Machine shape to start from:** `qemu-system-x86_64 -accel tcg,thread=multi -machine q35 -smp 2 -m 3072`, virtio disk, two virtio-net NICs, `-display none`. Start with the default `qemu64` CPU model (what the FreeBSD Handbook example uses) and treat `-cpu max` as a probe variable. 3 GB is the documented OPNsense minimum.
4. **Console and control:** serial on a Unix socket (`-serial unix:<path>,server=on,wait=off`) or stdio for interactive use, plus a QMP socket for scripted `savevm`/`loadvm`/`system_reset`/`quit`.
5. **Network, no root:** first NIC (OPNsense LAN by default) on `-netdev user` renumbered to OPNsense's default LAN subnet, with `restrict=on` and a `hostfwd` from `127.0.0.1:<port>` to `192.168.1.1:443` for the API and GUI. `restrict=on` isolates the guest from the host and the outside while explicit forwards keep working. Second NIC (WAN) either on a second user-mode netdev (gives DHCP and outbound NAT, only if firmware or plugin fetches are wanted) or left unplugged.
6. **Reset:** keep the converted image read-only as a golden base; run from a qcow2 overlay (`qemu-img create -f qcow2 -b base.qcow2 -F qcow2 run.qcow2`) and delete the overlay to cold-reset. Once the API answers, take a `savevm` snapshot and measure `-loadvm` resume time: if TCG boot is slow, warm-restore is what makes a test loop bearable.
7. **Measure and record** (these are the ticket's open numbers): power-on to serial login; power-on to first HTTP 200 from the API; latency of a handful of representative read-only API calls; idle host CPU per vCPU thread; resident memory of the QEMU process; `savevm`/`loadvm` time; and whether `sysctl kern.vm_guest kern.hz` inside the guest shows VM detection and `hz=100`.
8. **Kill criteria:** if API calls routinely time out at default client timeouts, or boot-to-API is long enough that even `loadvm` cannot rescue a test loop, record "not viable as the primary lab" with the numbers and reopen ADR 0001's consequences.

## Findings

### 1. amd64 on this Mac means TCG, and that is a supported QEMU configuration

- QEMU's accelerator table lists `hvf` for macOS hosts on x86 and Arm, and `tcg` for Linux, other POSIX, Windows, and macOS hosts on Arm and x86 among others. Source: [QEMU system emulation introduction](https://www.qemu.org/docs/master/system/introduction.html).
- HVF is a virtualization accelerator for same-architecture guests; UTM's docs state the rule plainly: "When the target architecture matches the host, you can use the hypervisor to enable virtualization." Source: [UTM QEMU settings](https://docs.getutm.app/settings-qemu/qemu/). A UTM issue thread asks and nobody contradicts that HVF cannot be used for x86 guests on Apple Silicon ([utmapp/UTM#5468](https://github.com/utmapp/UTM/issues/5468), anecdotal).
- OPNsense officially supports only amd64: "OPNsense is available for x86-64 (amd64) bit microprocessor architectures." Source: [OPNsense hardware requirements](https://docs.opnsense.org/manual/hardware.html). Its virtualization page lists ESXi, Xen, Hyper-V, and KVM (both i440FX and Q35 machine types), and says it installs on any hypervisor that supports FreeBSD. It does not mention emulation or Arm. Source: [OPNsense virtual installs](https://docs.opnsense.org/manual/virtuals.html).

### 2. Multi-core TCG for an x86 guest on an Arm host

- The `-accel tcg,thread=single|multi` option: "When the TCG is multi-threaded there will be one thread per vCPU therefore taking advantage of additional host cores. The default is to enable multi-threading where both the back-end and front-ends support it and no incompatible TCG features have been enabled (e.g. icount/replay)." Source: [QEMU invocation](https://www.qemu.org/docs/master/system/invocation.html), text verified in [`qemu-options.hx` at v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx).
- Source check: the i386 target declares `.mttcg_supported = true` ([`target/i386/tcg/tcg-cpu.c` v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/tcg/tcg-cpu.c)), and the default branch in `tcg_init_machine` enables MTTCG when `mttcg_supported && !icount_enabled()`, with no host-memory-order test ([`accel/tcg/tcg-all.c` v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/accel/tcg/tcg-all.c)). The aarch64 backend declares `TCG_TARGET_DEFAULT_MO 0`, meaning it makes no ordering promises and the guest's required ordering has to be provided by emitted barriers ([`tcg/aarch64/tcg-target-mo.h` v10.1.0](https://github.com/qemu/qemu/blob/v10.1.0/tcg/aarch64/tcg-target-mo.h)).
- Discrepancy to be aware of: the developer doc still describes the default as conditional on the host memory model accommodating the guest, and warns that for "a strongly ordered guest architecture being emulated on a weakly ordered host the scope for a heavy performance impact is quite high." Source: [Multi-threaded TCG](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html). Older QEMU really did fall back to single-threaded for this pairing ([qemu-project/qemu#1684](https://gitlab.com/qemu-project/qemu/-/issues/1684), reported against QEMU 5.2, closed 2023). Passing `thread=multi` explicitly removes the ambiguity.
- UTM exposes the same switch as "Force multicore", which "must be selected when attempting to emulate multiple cores of a strong memory system on a weak memory system (strong-on-weak)." Source: [UTM system settings](https://docs.getutm.app/settings-qemu/system/). UTM also has a "Use TSO" option, described as "an Apple Silicon hardware feature that enhances performance of x86 emulators" ([UTM QEMU settings](https://docs.getutm.app/settings-qemu/qemu/)). No equivalent option was found in upstream QEMU's option docs, so plain QEMU should be assumed not to have it.
- Anecdotal and mixed: in [utmapp/UTM#5468](https://github.com/utmapp/UTM/issues/5468) (open since 2023-07, last activity 2025-07) one user reports x86 guests under UTM on Apple Silicon sped up when given a single core, and a QEMU contributor suspects macOS-specific primitives rather than MTTCG itself. So "more vCPUs" is not guaranteed to be faster; the probe should compare `-smp 1` and `-smp 2`.
- Each TCG VM reserves a translation cache: default is the lesser of 1 GiB and one eighth of host RAM, tunable with `tb-size` ([`tcg/region.c` v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/tcg/region.c)).

### 3. FreeBSD under QEMU TCG: what is documented, what to watch

- The FreeBSD Handbook's QEMU chapter runs FreeBSD amd64 guests entirely under TCG ("All the examples in this section used the Tiny Code Generator (tcg) accelerator as that is the only supported accelerator on FreeBSD at present"), with `-cpu qemu64`, `-smp 4`, `virtio-blk-pci` disk, and an `e1000` NIC, and covers serial console (`-nographic`), the monitor, and `savevm`/`loadvm` snapshots. Source: [FreeBSD Handbook, Virtualization](https://docs.freebsd.org/en/books/handbook/virtualization/) ([source](https://github.com/freebsd/freebsd-doc/blob/main/documentation/content/en/books/handbook/virtualization/_index.adoc)). That is an x86 host, but the guest-visible machine is the same one TCG presents on an Arm host.
- **Timer tick rate.** The Handbook calls lowering `kern.hz` "the most important step" for reducing FreeBSD guest CPU use (written for Parallels and Fusion, `kern.hz=100`). FreeBSD already does this automatically when it detects a hypervisor: `hz = vm_guest > VM_GUEST_NO ? HZ_VM : HZ`, with `HZ_VM` 100 and `HZ` 1000 ([`sys/kern/subr_param.c`](https://github.com/freebsd/freebsd-src/blob/releng/15.0/sys/kern/subr_param.c)). QEMU's TCG CPU sets the CPUID hypervisor bit and a `TCGTCGTCGTCG` signature ([`target/i386/cpu.c` v11.1.0](https://github.com/qemu/qemu/blob/v11.1.0/target/i386/cpu.c)), so detection should fire, but that is an inference: verify `kern.vm_guest` and `kern.hz` in the probe, and set `kern.hz=100` as a tunable if it does not. One first-hand report of FreeBSD under QEMU on Apple Silicon (aarch64 guest, HVF) saw heavy idle CPU until `kern.hz=100` was set ([Antranig Vartanian, 2022](https://antranigv.am/posts/2022/11/running-arm64-aarch64-freebsd-on-qemu-utm-app-on-apple-silicon/), anecdotal; the same author says amd64 FreeBSD under emulation "gets the job done").
- **CPU model.** Without `-cpu`, x86_64 guests get `qemu64` ([QEMU x86 CPU models](https://www.qemu.org/docs/master/system/i386/cpu.html)). `host` is KVM/HVF only; `max` under TCG means "best possible emulation" (stated for Arm at [virt machine docs](https://www.qemu.org/docs/master/system/arm/virt.html); the x86 page does not spell out TCG guidance). No source was found saying OPNsense or FreeBSD 15 needs more than `qemu64`. Unknown until booted.
- **virtio and offloads.** OPNsense's own guidance for virtual installs is to "Disable all hardware off-loading settings in Interfaces > Settings", and it documents falling back from paravirtual NICs to E1000 when problems appear ([OPNsense virtual installs](https://docs.opnsense.org/manual/virtuals.html)). Start with virtio-net; keep e1000 as the fallback.
- **Timekeeping and "runtime went backwards".** Old list traffic shows FreeBSD amd64 guests under QEMU logging `calcru: runtime went backwards` ([qemu-discuss, 2013](https://lists.gnu.org/archive/html/qemu-discuss/2013-06/msg00026.html), anecdotal and old). No current upstream bug specific to FreeBSD amd64 on an arm64 macOS TCG host was found. Treat clock drift and timecounter choice as something to observe, not a known defect.
- OPNsense 26.7 is based on "FreeBSD 15.1-RELEASE-p1 plus assorted stable/15 networking commits" per its [release announcement](https://forum.opnsense.org/index.php?topic=52375.0), which also warns of Hyper-V guest panics with more than one vCPU. That note is Hyper-V specific, but it is a reminder that vCPU count is a variable worth testing.

### 4. Boot and API responsiveness: what can honestly be said

- No primary source gives OPNsense boot or API timings under TCG. None are asserted here.
- OPNsense-specific, **anecdotal**: a 2021 forum user ran OPNsense in UTM on an M1 MacBook Air: it runs, "allerdings gefühlt sehr langsam" (feels very slow), acceptable to them for home use ([OPNsense forum topic 24517](https://forum.opnsense.org/index.php?topic=24517.0)). Another Apple Silicon thread turned out to be a native arm64 image under VMware Fusion, not emulation ([topic 32765](https://forum.opnsense.org/index.php?topic=32765.0)).
- General x86-on-Apple-Silicon, **anecdotal**: in [utmapp/UTM#5468](https://github.com/utmapp/UTM/issues/5468) a Windows XP guest booted in roughly 21 to 28 s under Homebrew `qemu-system-x86_64` with TCG on an M1 Max versus roughly 50 to 60 s under UTM. That is a different, much lighter guest; it supports "plain QEMU is faster than UTM", not any OPNsense number. UTM discussions such as [#2533](https://github.com/utmapp/UTM/discussions/2533) and [#4349](https://github.com/utmapp/UTM/discussions/4349) carry many "extremely slow" complaints, mostly about desktop guests.
- Lima's docs on the same mechanism: "Running a VM with a foreign architecture is extremely slow" ([Lima multi-arch](https://lima-vm.io/docs/config/multi-arch/)). Docker's docs say emulated Intel containers "will be slower and use more memory than the native equivalent" ([Docker Desktop known issues](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/known-issues/)).
- Reasoned expectation, not evidence: OPNsense's boot and its PHP-driven configuration layer are CPU-bound, so they will be the slow part; a read-only API client is latency-tolerant and drives no packet throughput, which is the case emulation hurts most. The M4 Pro is a faster host than the M1 machines in the reports above.

### 5. Headless scripting options

**Plain QEMU (recommended).**
- Console: `-nographic` "Totally disable graphical output so that QEMU is a simple command line application. The emulated serial port is redirected on the console and muxed with the monitor" ([QEMU invocation](https://www.qemu.org/docs/master/system/invocation.html)). The same page documents `-serial` backends (stdio, pty, Unix and TCP sockets, telnet) and the QMP/monitor sockets.
- OPNsense side: the `serial` image "boots into live environment running in serial console (115200) mode only"; the `nano` image is "for preinstalling onto >=4 GB USB drives, SD, or CF cards" and images "can be installed and run from virtual disks (VM)" ([OPNsense install docs](https://docs.opnsense.org/manual/install.html)). The build hook for nano sets `<primaryconsole>serial</primaryconsole>`, `<secondaryconsole>video</secondaryconsole>`, and memory-backed `/tmp` and `/var` ([opnsense/tools `config/26.7/extras.conf`](https://github.com/opnsense/tools/blob/master/config/26.7/extras.conf)). Default login is `root` / `opnsense`, the first interface is LAN at `192.168.1.1/24`, the second is WAN (install docs).
- Official images on the mirror are `dvd`, `nano`, `serial`, `vga`, amd64 only, with checksums and signatures ([pkg.opnsense.org/releases/mirror](https://pkg.opnsense.org/releases/mirror/)). Official VM-format images are deliberately not published: "Virtual machine images come in varying disk formats and sizes. For this reason they are not included in our binary releases" ([opnsense/tools README](https://github.com/opnsense/tools#readme)).
- Snapshots and reset: `-snapshot` writes to temporary files instead of the image; VM snapshots (`savevm`/`loadvm`/`delvm`, or `-loadvm` at start) need a writable qcow2 disk and capture "CPU state, RAM, device state and the content of all the writable disks" ([QEMU disk images](https://www.qemu.org/docs/master/system/images.html)). qcow2 backing files give cheap cold reset.
- Networks, all from [QEMU invocation](https://www.qemu.org/docs/master/system/invocation.html) and [`qemu-options.hx`](https://github.com/qemu/qemu/blob/v11.1.0/qemu-options.hx):
  - **User-mode (slirp):** no privileges; `hostfwd=[tcp|udp]:[hostaddr]:hostport-[guestaddr]:guestport`; `restrict=on` means "the guest will be isolated, i.e. it will not be able to contact the host and no guest IP packets will be routed over the host to the outside. This option does not affect any explicitly set forwarding rules." Best fit for host-to-API access.
  - **Socket family:** `-netdev socket` with `listen`/`connect` (TCP, point to point), `mcast` (UDP multicast, "effectively making a bus for every QEMU with same multicast address"), and the newer `-netdev stream` / `-netdev dgram` including Unix-socket variants. No privileges; architecture-agnostic, so they are the natural way to wire clients to the firewall's LAN.
  - **vmnet (macOS only):** `vmnet-host` (with `isolated=on|off` and `net-uuid` to build a private DHCP-less segment), `vmnet-shared` (NAT), `vmnet-bridged`. But Apple restricts the API: the `com.apple.vm.networking` entitlement "is required to use the vmnet APIs" and "is restricted to developers of virtualization software" ([Apple entitlement docs](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.vm.networking)). In practice "QEMU-builtin vmnet requires running the entire QEMU process as root"; [lima-vm/socket_vmnet](https://github.com/lima-vm/socket_vmnet) avoids that with a root daemon instead. Either way it needs sudo, so keep vmnet out of the probe.
  - **VDE:** Homebrew's QEMU is built with `--enable-vde` ([formula](https://github.com/Homebrew/homebrew-core/blob/HEAD/Formula/q/qemu.rb)), which offers an unprivileged userspace switch for segments with more than two members.

**UTM.** A GUI app wrapping QEMU. Automation is AppleScript, Shortcuts, and `utmctl`, a CLI wrapper over AppleScript ([UTM scripting](https://docs.getutm.app/scripting/scripting/), [reference](https://docs.getutm.app/scripting/reference/)). `utmctl` has start (including a disposable mode), stop, suspend, clone, delete, and serial `attach`; guest exec, file, and IP queries need the QEMU guest agent; and its source says "utmctl does not work from SSH sessions or before logging in" ([`UTMCtl.swift`](https://github.com/utmapp/UTM/blob/main/utmctl/UTMCtl.swift)). Snapshot subcommands exist on `main` but were not confirmed in a released version. "Not all features are currently supported in the automation interface." UTM's x86 emulation is reported slower than plain QEMU in a still-open issue (section 4). Its one potential advantage is the TSO option. Verdict: fallback and a useful comparison point, not the base.

**Lima.** FreeBSD guests are experimental since v2.1 ([Lima experimental features](https://lima-vm.io/docs/releases/experimental/)), and the FreeBSD template uses FreeBSD's `BASIC-CLOUDINIT` images with `vmType: qemu` ("Apparently does not boot with vz") ([template](https://github.com/lima-vm/lima/blob/master/templates/_images/freebsd-15.yaml)). Lima's model assumes cloud-init and SSH provisioning of the guest; OPNsense images provide neither by default. Poor fit for the firewall. It could still manage Linux client VMs, but plain QEMU does that with less machinery.

**Packer (for the later reproducible lab, not the probe).** The QEMU builder accepts `accelerator = "tcg"` and `qemu_binary`, but `boot_command` is typed over VNC and "cannot be used when [disable_vnc] is true" ([Packer QEMU builder](https://developer.hashicorp.com/packer/integrations/hashicorp/qemu/latest/components/builder/qemu)). Timed keystrokes against a slow emulated guest are fragile; a serial-console `expect`-style driver or the preinstalled nano image sidesteps that.

### 6. Memory and CPU budget

- Firewall: OPNsense's documented minimum is 3 GB RAM ("a minimum of 3 GB memory is needed for the installer to run"; virtual installs: "Minimum required RAM is 3 GB", minimum recommended virtual disk 8 GB) ([hardware](https://docs.opnsense.org/manual/hardware.html), [virtual installs](https://docs.opnsense.org/manual/virtuals.html)). Add the TCG translation cache (up to 1 GiB by default, section 2) and QEMU's own overhead. Plan on roughly 4 to 4.5 GB of host memory for the firewall. Note the nano image keeps `/tmp` and `/var` in RAM, so do not go below the minimum.
- Clients: **mixing is practical.** Each VM is its own QEMU process, and the socket/stream/dgram/VDE backends carry Ethernet frames regardless of guest architecture or accelerator, so clients can be native arm64 guests run with `qemu-system-aarch64 -machine virt -accel hvf -cpu host` (the `virt` board is "the recommended board type if you simply want to run a guest such as Linux"; `-cpu host` works with "KVM and HVF only": [QEMU virt docs](https://www.qemu.org/docs/master/system/arm/virt.html)). Alpine publishes an aarch64 "Virtual" flavour, "Slimmed down kernel. Optimized for virtual systems" ([Alpine downloads](https://alpinelinux.org/downloads/)). A few hundred MB each is a reasonable planning figure for such clients; this is an estimate, not a cited requirement. For traffic that only needs a network namespace's worth of client, containers are cheaper still, but they cannot join a QEMU socket network without extra plumbing.
- Total: about 4.5 GB for the firewall plus about 1.5 GB for three clients, so roughly 6 GB of 24 GB, leaving ample room for macOS, the toolchain, and Docker Desktop if it is running (its VM reserves its own configured memory). CPU: two TCG vCPU threads can saturate two performance cores during boot and config reloads; the M4 Pro's 8 performance cores absorb that. A second emulated firewall (for an upgrade fixture or HA later) fits in memory; whether it fits in patience depends on the probe's numbers.

### 7. aarch64 OPNsense: exists, unofficial, not an acceptable target

- The official package mirror carries only amd64 ABIs for current series (`FreeBSD:14:amd64`, `FreeBSD:15:amd64`; the only Arm entry is a stale `FreeBSD:11:armv6` from 2019) ([pkg.opnsense.org](https://pkg.opnsense.org/)), and official release images are amd64 only ([mirror](https://pkg.opnsense.org/releases/mirror/)).
- The official build tools do contain Arm device configs (`ARM64.conf`, `RPI.conf`, and others) and a cross-building section ([opnsense/tools](https://github.com/opnsense/tools/tree/master/device)), so aarch64 is buildable from source, but no official binaries or updates result from that.
- The maintained community effort is [maurice-w/opnsense-vm-images](https://github.com/maurice-w/opnsense-vm-images) (a fork of opnsense/tools; 26.7 aarch64 qcow2 images with EFI or serial console published 2026-07-16) backed by a third-party firmware repository, [opnsense-update.walker.earth](https://opnsense-update.walker.earth/), signed with that maintainer's own key. Both say in capitals that these builds "are not supported by Deciso or the OPNsense core team"; in the [announcement thread](https://forum.opnsense.org/index.php?topic=35828.0) the maintainer says he tests on Ampere-based cloud VMs, and the OPNsense lead's reply is thanks, not adoption.
- Why it is not an acceptable compatibility target: the project's compatibility claim is about official Community releases, which are amd64; an aarch64 build has a different kernel, driver set, and package builds, a third-party trust root, and a plugin set compiled by a third party, so an API or config difference found (or missed) there proves nothing about what users run. It would also put an unofficial binary in the evidence chain of a tool whose selling point is version-accurate inspection.
- Where it could still help: as an optional, clearly labelled fast inner loop under HVF for work that is architecture-independent (API shapes, MCP plumbing), with anything that counts re-run on emulated amd64. Only worth considering if the probe shows emulation is painful. This is a suggestion, not a finding.

### 8. Running the x86 VM inside Docker Desktop's Linux VM: hurts

- On Apple Silicon, Docker Desktop's Linux VM is arm64, and amd64 content runs under emulation that Docker itself calls "best effort": emulated Intel containers "can crash as QEMU sometimes fails to run the container", "`inotify` ... do not work under QEMU emulation", and they are "slower and use more memory" ([Docker Desktop known issues](https://docs.docker.com/desktop/troubleshoot-and-support/troubleshoot/known-issues/)). Docker VMM "does not currently support Rosetta, so emulation of amd64 architectures is slow" ([Docker VMM docs](https://docs.docker.com/desktop/features/vmm/)).
- A `qemu-system-x86_64` inside a container there is still pure TCG. Apple's nested virtualization "is available for Mac with the M3 chip, and later" (macOS 15+) ([Apple docs](https://developer.apple.com/documentation/virtualization/vzgenericplatformconfiguration/isnestedvirtualizationsupported)), but nested virtualization on an Arm host can only accelerate Arm guests, so it cannot help an amd64 firewall. Rosetta translates Linux user-space binaries, not a whole x86 machine with a FreeBSD kernel.
- Net effect: same emulation cost, plus a VM layer, plus the Docker VM's memory cap, plus losing macOS-side options (vmnet, direct Unix sockets to the host, simple `hostfwd` to localhost). The only upside would be a Linux-identical QEMU command line for CI parity, which plain QEMU on macOS already nearly provides.

## Risks and unknowns only the probe VM can settle

1. **Speed, the deciding one.** Boot-to-login, boot-to-API, per-call API latency, and config-reload time under TCG on the M4 Pro. No trustworthy numbers exist.
2. **`-smp 1` versus `-smp 2` (or more).** MTTCG is on by default but strong-on-weak barriers and macOS threading may eat the gain; there are anecdotal reports both ways.
3. **Does UTM's TSO mode beat plain QEMU** enough to matter? Only worth testing if plain QEMU disappoints.
4. **FreeBSD 15.1 under TCG on arm64 macOS:** VM detection and `kern.hz`, idle CPU burn, timecounter selection, clock drift, any `calcru` noise, and whether `qemu64` is sufficient or `-cpu max` helps or hurts.
5. **virtio-net and virtio-blk behaviour** in OPNsense under TCG, with offloads disabled per OPNsense guidance; e1000 as fallback.
6. **`savevm`/`loadvm` under TCG:** time taken and whether the restored guest's clock and network state are sane. This decides the reset strategy for the future Inspect-driven lab.
7. **Nano versus a full install.** Nano is preinstalled and serial-first but uses memory disks for `/tmp` and `/var` and a small UFS root; confirm nothing the inventory needs behaves differently, or do a one-time serial install to make the golden image.
8. **Multi-VM segments without root.** Whether `-netdev socket,mcast` works reliably on macOS, versus point-to-point `stream`/`dgram` Unix sockets or a VDE switch. Not needed for the single-VM probe; needed before clients are added.
9. **Slirp renumbered onto OPNsense's default LAN** (`net=192.168.1.0/24` with OPNsense's own DHCP server on that interface): check that `hostfwd` to `192.168.1.1:443` works with `restrict=on` and that the two DHCP servers do not fight.
10. **Real memory footprint** of the QEMU process (guest RAM plus translation cache) versus the planning figure.

## Method and limits

Sources were read on 2026-09-19. QEMU behaviour was checked against both the published docs and tagged source (v10.1.0 and v11.1.0, the latter matching Homebrew's 11.1.1 series). The QEMU wiki and FreeBSD wiki were unreachable (bot protection), and Apple's documentation was read through its JSON data endpoint. Forum and issue-tracker material is labelled anecdotal wherever used. Nothing was installed, downloaded as an image, or executed beyond read-only host queries and fetching documentation and source text.
