# Upstream licenses and what OPNsense Pilot may redistribute

Research for issue #9. Researched 2026-09-19. Feeds the license decision in #17.

> **Not legal advice.** This is an engineering reading of license texts, repository
> files, and the published OPNsense trademark policy. It identifies obligations and
> risks so the owner can choose; it does not replace a lawyer where the stakes
> justify one (notably the trademark question and any redistribution of VM images).

## Summary

- **All four upstream repos are BSD-2-Clause at the repo level**: `opnsense/core`,
  `opnsense/plugins`, `opnsense/docs` (documentation text too, not only code) and
  `opnsense/tools`. Each has a root `LICENSE` with the 2-clause text; `core` and
  `docs` READMEs say contributions must be under the same terms.
- **The repos are not pure BSD-2-Clause.** `core` bundles MIT, BSD-3-Clause,
  Apache-2.0, CC BY 4.0 / SIL OFL 1.1 and public-domain material (mostly web
  assets and `contrib/`). `plugins` contains an MIT plugin (`security/crowdsec`)
  and one plugin under a custom **no-modification** license
  (`security/intrusion-detection-content-pt-open`). The parts Pilot cares about
  (MVC controllers, models, legacy PHP, scripts) are BSD-2-Clause, by per-file
  header almost everywhere and by the root `LICENSE` otherwise.
- **Source excerpts, doc excerpts, generated API catalogs and citations are all
  permitted** under BSD-2-Clause. The only condition is to retain the copyright
  notice, the two conditions and the disclaimer. Practical compliance: record
  license + copyright per ingested artifact, and ship a `THIRD-PARTY-NOTICES`
  file reproducing the upstream `LICENSE` files verbatim.
- **Installation media are an aggregate, not BSD-2-Clause.** The image contains
  FreeBSD base plus packages that `core` hard-depends on, including GPLv2
  (suricata, dnsmasq, openvpn, strongswan), GPLv2+/LGPL (syslog-ng) and AGPLv3
  (monit). Redistributing an image makes us a binary distributor of those with
  corresponding-source duties, and a modified image still branded "OPNsense"
  raises a trademark problem. **Ship build recipes that download the official
  image and verify its checksum; do not publish VM images.**
- **Trademark is the sharpest constraint.** The policy says "OPNsense® is a
  registered trademark" and: "You must request our permission to use derivatives
  of the name and/or logo at project@opnsense.org prior to any use." "OPNsense
  Pilot" / `opnsense-pilot` / `opnsense_pilot` is plausibly a derivative of the
  name. The policy also allows using the name "to promote or serve OPNsense or
  related projects and their communities", so permission is likely obtainable,
  but it should be **requested by email before public release**.
- **Every common license for our own code is compatible with the inbound
  BSD-2-Clause material**: BSD-2-Clause, MIT, Apache-2.0, GPL-3.0, AGPL-3.0 all
  work. The choice is driven by other things: whether we reuse a GPL/AGPL client
  (`mtreinish/pyopnsense` is GPL-3.0-or-later), whether we want a patent grant
  (Apache-2.0), whether we want to match upstream so code can flow back
  (BSD-2-Clause), and whether we want network copyleft on a self-hosted service
  (AGPL-3.0).

  plugins.git ... create sets, packages and images". Image targets are `dvd`,
  `serial`, `vga`, `nano`, `vm` (vmdk default, other formats available).
- The build is parameterised for rebranding (`core:Mk/version.mk` has
  `CORE_PRODUCT?= OPNsense`, `CORE_NAME`, `CORE_WWW`; the license view only adds
  "®" when the product name is `OPNsense`). Upstream expects forks to rename.

## 2. Installation media

There is **no separate license statement for the images**. The download page
lists mirrors and checksums only; the site terms and conditions are Deciso Sales
B.V. commercial terms (shop, subscriptions, export control) and do not address
the community images. The legal pages describe the composition:

- "OPNsense is based on FreeBSD, Copyright © The FreeBSD Project."
- "OPNsense includes various freely available software packages and ports. The
  current ports are listed in a file named `ports.conf`" (in `opnsense/tools`
  `config/<version>/`).

So an image is an aggregate of separately licensed works:

- FreeBSD base and kernel from `opnsense/src`. Its `COPYRIGHT` file states the
  compilation is BSD-2-Clause and then lists further notices; FreeBSD's `contrib/`
  and `sys/contrib/` trees carry their own licenses. Not audited here.
- `opnsense` core package and plugins: BSD-2-Clause as above.
- About 278 port entries in `tools:config/26.7/ports.conf`. `LICENSE=` lines read
  from `opnsense/ports` Makefiles at the pinned SHA:

  | Port | `LICENSE=` | In `core:Mk/version.mk` `CORE_DEPENDS`? |
  | --- | --- | --- |
  | `opnsense/suricata` | GPLv2 | yes |
  | `opnsense/dnsmasq` | GPLv2 | yes |
  | `security/openvpn` | GPLv2 | yes |
  | `security/strongswan` | GPLv2 | yes |
  | `sysutils/syslog-ng` | GPLv2+ and LGPL21+ | yes |
  | `sysutils/monit` | AGPLv3 | yes |
  | `net/isc-dhcp44-server` | MPL20 | not checked |
  | `shells/bash` | GPLv3+ | not checked |
  | `security/sudo` | sudo (ISC-style) | not checked |
  | `security/openssl` | APACHE20 | not checked |
  | `lang/python311` | PSFL | not checked |
  | `dns/unbound`, `www/lighttpd` | BSD3CLAUSE | not checked |
  | `sysutils/cpu-microcode-intel` | EULA | built as a port/plugin; not confirmed to be in the base image |

  On an installed system `core:src/opnsense/scripts/firmware/license.sh` prints
  each package's license text from `pkg`'s license directory, which is how
  upstream meets per-package notice duties inside the product.

Consequences for us:

- **Downloading and running the image locally** (the ADR 0001 lab) needs no
  permission beyond what every user has.
- **Redistributing an image** (unmodified or pre-configured, including a Packer
  output, a Vagrant box or a container layer that embeds it) makes us a
  distributor of GPLv2, GPLv3 and AGPLv3 binaries. GPLv2 section 3 and GPLv3
  section 6 then require us to provide or offer corresponding source for those
  exact binaries, and all other notices must travel with the image. That is a
  real, ongoing obligation for zero product benefit.
- **A modified image still called "OPNsense"** is also a trademark problem: a
  pre-seeded config, extra packages or an added API key make it no longer the
  product the mark owner shipped.
- **Recommendation: publish recipes only.** A Packer/QEMU template that fetches
  the official image from an official mirror, verifies the published SHA-256,
  and configures it locally redistributes nothing. Do not commit images, do not
  attach them to releases, do not cache them in a public CI artifact store or
  container registry.

## 3. What Pilot may ship or publish

BSD-2-Clause grants "Redistribution and use in source and binary forms, with or
without modification" on two conditions: source redistributions "must retain the
above copyright notice, this list of conditions and the following disclaimer";
binary redistributions must reproduce them "in the documentation and/or other
materials provided with the distribution". There is no copyleft, no
no-endorsement clause (that is the third clause, absent here), no patent
language, and no trademark grant.

| Artifact | May we ship/publish it? | Obligation |
| --- | --- | --- |
| Source excerpts from `core`/`plugins`/`tools` in a published corpus, in evidence bundles, in reports | Yes. An excerpt is a redistribution of part of the source, with or without modification. | Retain notice + conditions + disclaimer. See "Attribution mechanics" below. |
| Evidence citations (repo URL, commit, path, line range, short quote) | Yes. A citation plus a short quote is the lowest-risk form and is also what the handoff's evidence model wants. | Same as above for the quoted text; the pointer itself carries no obligation. |
| Documentation excerpts (text) | Yes. The docs text is BSD-2-Clause, which is unusually permissive for documentation. | Same. Use the *docs* `LICENSE` wording, which differs slightly from the code one. |
| Documentation images, screenshots, logos | Avoid. CC0 applies to "some pictures" without saying which; logos are explicitly not licensed. | n/a |
| Generated API catalogs derived from controllers/models | Yes. Endpoint names and field names are close to bare facts, but the safe assumption is that a catalog generated from BSD-2-Clause source is a derivative redistribution. | Same notice. State the generator, the upstream repo and the commit the catalog was generated from. |
| Sanitized config fixtures derived from real systems | Yes as far as upstream licensing goes. A `config.xml` is the operator's own data; its element structure comes from `core`'s models and sample config, which are BSD-2-Clause. | Include upstream notice in the fixtures directory to be safe. The real constraints are privacy and consent: only the owner's own config, fully redacted, never a third party's without permission. |
| Synthetic fixtures written by us | Yes; they are our work under our license. | None upstream. |
| VM images, boxes, pre-installed disks | **No** (see section 2). | GPL/AGPL corresponding source, all package notices, trademark. |
| Build recipes that fetch the official image | Yes; our own code. | None, beyond not implying endorsement. |
| Embeddings / vector indexes computed from upstream text | No license in play forbids it. If a published corpus snapshot includes the text alongside vectors, the text obligations above apply to that snapshot. | As for excerpts. |
| `security/intrusion-detection-content-pt-open` content | Verbatim only; no modified redistribution. | Keep out of the corpus. |

### Attribution mechanics (one approach that satisfies every row)

1. `THIRD-PARTY-NOTICES` (or `NOTICE`) at the repo root reproducing, verbatim,
   the `LICENSE` file of each ingested upstream repo **at the ingested ref**,
   because the copyright-holder list changes between releases (it is
   regenerated by `Scripts/license`).
2. Per `SourceArtifact` in the corpus: repository URL, commit, path, SPDX
   identifier, and the file's own copyright lines where a per-file header exists.
   The handoff already specifies storing `license` per artifact (section on
   ingestion, step 2); add the copyright lines and a pointer to the notice text.
3. Any exported or published corpus snapshot, and any binary distribution of
   Pilot that embeds corpus data (wheel, container image), includes that notices
   file. This is the "documentation and/or other materials" route of clause 2.
4. Evidence bundles returned over MCP/REST carry the citation and SPDX id; the
   full disclaimer does not need to be repeated per chunk as long as the
   distribution that contains the chunk carries it once.
5. The ingester refuses or flags files whose header is not BSD-2-Clause/MIT
   (Apache-2.0, custom licenses, no-modification terms) instead of silently
   inheriting the repo-level license.

## 4. Trademark constraints on "OPNsense Pilot"

Policy text, identical on <https://opnsense.org/legal-guidelines/> and in
`docs:source/legal.rst`, except that the website says "OPNsense® is a registered
trademark" where the docs say "OPNsense is a trademark":

1. "The name and logo may be used to promote OPNsense based products or
   services."
2. "The name and logo may be used to promote or serve OPNsense or related
   projects and their communities."
3. "When using the logo on online media like websites, social media and apps the
   logo should link to https://opnsense.org"
4. "You must request our permission to use derivatives of the name and/or logo
   at project@opnsense.org prior to any use of the derivative name and/or logo,
   and we may grant or withhold permission ... in our sole discretion."
5. "You may not state or otherwise lead people to believe, that you represent the
   OPNsense project in any way other than as an individual or corporate
   contributor to the project."

Reading:

- None of the BSD-2-Clause licenses grants any trademark right. The trademark
  policy is the only permission there is.
- Describing what the tool works with ("an inspection tool for OPNsense®") is
  covered by rule 2 and is ordinary referential use.
- **A project, package and repository named "OPNsense Pilot" / `opnsense-pilot` /
  `opnsense_pilot` is a new name built from the mark.** That is the natural
  meaning of "derivatives of the name", and rule 4 requires permission *before*
  use, at the mark owner's sole discretion. Rule 2 makes a grant plausible for a
  free, read-only community tool, but it does not remove the requirement to ask.
- Many community projects embed the name without visible permission (the #6
  candidates include `pyopnsense`, `OPNSenseMCP`, `opnsense-mcp-server`). That
  shows tolerance, not a license. A project that aims to be the cited, trusted
  reference is better off with an explicit yes.
- Package registries (PyPI, container registries) add a practical risk: a name
  that infringes can be taken down on complaint, which is costly once users
  depend on it.

Recommended handling, in order of preference:

1. Email project@opnsense.org before the repo is promoted publicly: describe the
   project (open source, read-only, non-commercial, cites official sources),
   ask for permission to use "OPNsense Pilot" as project name and
   `opnsense-pilot`/`opnsense_pilot` as package names, and record the reply in an
   ADR.
2. Regardless of the answer: README and docs carry "OPNsense® is a registered
   trademark of its owner. OPNsense Pilot is an independent project, not
   affiliated with or endorsed by the OPNsense project or Deciso B.V."; do not
   use the OPNsense logo (if ever used, it must link to opnsense.org); never use
   a name or styling that reads as an official product.
3. Fallback if permission is refused or unanswered: a name where the mark is
   only referential, e.g. "Pilot for OPNsense" with a package name that does not
   start with the mark. Decide the fallback *before* publishing to PyPI, since
   renaming a package later is expensive.

The repo is already public under this name, so rule 4 is technically already
engaged; this is an argument for sending the email soon, not for alarm.

## 5. License options for Pilot's own code

Inbound compatibility is not the discriminator: BSD-2-Clause and MIT material can
be included in a work under any of the candidates, provided the notices are kept.
The excerpts themselves stay BSD-2-Clause; our license covers our code and our
original corpus metadata. The GNU license list confirms both the 2-clause BSD
("FreeBSD") and Expat/MIT licenses are "compatible with the GNU GPL", that
Apache-2.0 is "compatible with version 3 of the GNU GPL" but "not compatible with
GPL version 2", and that GPLv3 and AGPLv3 modules may be combined in one project.

Baseline dependencies from the handoff, as reported by GitHub's license API on
2026-09-19 (indicative; confirm at adoption): `UKGovernmentBEIS/inspect_ai` MIT,
`modelcontextprotocol/python-sdk` MIT, `MagicStack/asyncpg` Apache-2.0,
`psycopg/psycopg` LGPL-3.0. None of these constrains the candidates below, with
one exception: an Apache-2.0 dependency rules out GPL-2.0-only, which nobody is
proposing.

Reuse candidates (survey is #6, still open; licenses below are GitHub's detection
from each repo's license file, except pyopnsense which was read directly):

| Candidate | License | Effect if imported as a dependency |
| --- | --- | --- |
| `mtreinish/pyopnsense` | GPL-3.0-or-later (`LICENSE` and per-file headers) | The distributed combination must be GPLv3-compatible as a whole. Our files could still be permissive, but users receive Pilot under GPL terms. In practice this pushes us to GPL-3.0-or-later or AGPL-3.0. |
| `devinbarry/opn-api`, `fakebizprez/opnsense-mcp-server`, `gabrielion/OPNSenseMCP` | AGPL-3.0 | Combination must be AGPL-3.0 (or GPLv3 with the AGPL part remaining AGPL). Forces network-copyleft on Pilot. |
| `kisst/aioopnsense` | Apache-2.0 | Works with everything except GPL-2.0-only. NOTICE retention. |
| `vespo92/OPNSenseMCP`, `Pixelworlds/opnsense-mcp-server`, `lucamarien/opnsense-mcp-server`, `coreyhines/opnsense-mcp` | MIT | Works with everything. |
| several small MCP repos | no license detected | **Cannot be reused at all** (no license means no permission), only read for ideas. |

Trade-offs by candidate license for our own code:

| License | For | Against |
| --- | --- | --- |
| **BSD-2-Clause** | Identical to upstream: code, docs fixes and API-catalog tooling can flow back to `opnsense/*` with no friction ("Pull request must adhere to 2-Clause BSD licensing"). One license text across our code and the corpus notices. Simplest story for users. | No patent grant. No protection against closed forks or hosted proprietary derivatives. Cannot absorb GPL/AGPL client code. |
| **MIT** | Same practical effect as BSD-2-Clause; most familiar in the Python/MCP ecosystem; matches MCP SDK and Inspect AI. | Same as BSD-2-Clause, and not literally upstream's license, so an upstream contribution would need relicensing of that piece (trivial for a sole author). |
| **Apache-2.0** | Explicit patent grant with litigation termination (section 3); explicit "no trademark rights" clause (section 6), which suits a project with a name of its own to protect; contributor terms built in (section 5). Compatible with GPLv3/AGPLv3 consumers. | Heavier compliance for redistributors (section 4: license copy, change notices, NOTICE propagation). Not acceptable for direct upstream contribution without relicensing. Incompatible with GPL-2.0-only code. Cannot absorb GPL/AGPL code. |
| **GPL-3.0-or-later** | Lets us vendor or depend on `pyopnsense` cleanly. Forks that are distributed must stay open. | Does not reach hosted/network use, which is the main way a service like Pilot would be exploited. Deters some corporate adopters and integrators. Cannot contribute upstream without relicensing. Anyone embedding Pilot as a library inherits GPL. |
| **AGPL-3.0-or-later** | The only option that obliges someone running a modified Pilot as a network service to offer source (section 13); fits "self-hosted service exposing MCP/REST". Can absorb GPL-3.0 and AGPL clients. | Strongest adoption friction: many companies ban AGPL outright. MCP clients talking to Pilot over the network are not affected, but anyone linking Pilot's Python packages is. Same upstream-contribution and relicensing costs as GPL. A sole copyright holder can dual-license later; that ends once outside contributions arrive without a CLA. |

Questions that decide it (for #17):

1. **Does #20 adopt a GPL/AGPL client?** If yes, permissive licensing for the
   distributed whole is off the table. If we build our own connector or reuse an
   MIT/Apache one, all five options stay open.
2. **Is giving back upstream a goal?** If the API-catalog or docs tooling is meant
   to be contributed to `opnsense/*`, BSD-2-Clause (or MIT with ad hoc
   relicensing) is the low-friction choice.
3. **Is a closed hosted fork an outcome the owner wants to prevent?** Only AGPL
   addresses it. If not a concern, the copyleft options buy little.
4. **Is a patent grant wanted?** Apache-2.0 is the only permissive option with
   one. For a read-only inspection tool by an individual, patent exposure is low.
5. Whatever is chosen, **the corpus data keeps its upstream license**. Consider
   stating this split explicitly: "code under X; ingested upstream material under
   its original BSD-2-Clause terms, see THIRD-PARTY-NOTICES".

## Open questions

- **Trademark permission**: not requested yet. Who the registered owner is, and
  in which registries/classes, was not verified; neither legal page names the
  owner in the trademark section (Deciso B.V. is named as *copyright* holder). A
  registry lookup (EUIPO, USPTO) is cheap and would tell us whom the permission
  must come from.
- **Exact composition of the chosen release image** (#3): which packages and
  firmware are actually on the DVD/VGA/VM image, versus merely built into the
  package repository. Only matters if the "recipes only" recommendation is
  rejected.
- **FreeBSD base (`opnsense/src`) third-party licenses** were not audited beyond
  the top-level `COPYRIGHT`. Irrelevant unless we redistribute images or ingest
